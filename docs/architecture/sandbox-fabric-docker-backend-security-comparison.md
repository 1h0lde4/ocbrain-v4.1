# Sandbox / Execution Fabric — NamespaceBackend vs. a Future DockerBackend: Security Comparison

**Status:** Prerequisite analysis for step 3 of the sandbox-fabric sequence (DockerBackend). No Docker code exists yet; this document is what that work is gated on.
**Date:** September 14, 2026
**Scope:** Isolation-guarantee-by-isolation-guarantee comparison between `core/sandbox/backends/namespace_backend.py` (built and adversarially tested in this environment) and Docker's actual behavior (established from Docker/Moby's own source, documentation, and a live 2026 CVE response — not tested directly, since `docker`/`runc`/`podman` remain absent from this build environment, confirmed repeatedly throughout this branch's history).
**Method:** Every claim about `NamespaceBackend` below is something this branch already built and adversarially tested (see reconciliation §§2–9). Every claim about Docker is sourced from Docker/Moby's own repositories, PRs, and documentation, current as of this writing — marked as **[Docker, documented]** throughout to keep the two epistemic categories visually distinct, since only one of them has been verified empirically in this environment. Where a Docker claim could not be corroborated from a primary source, it is marked **[Docker, unverified]** rather than stated as fact.

---

## 1. Why this document exists

`docs/architecture/sandbox-execution-fabric-existing-code-reconciliation.md` §6 deferred the Docker backend explicitly: *"kept fully separate, requiring its own explicit backend-security comparison before inheriting any assumption from this namespace/seccomp backend."* This is that comparison. It does not implement `DockerBackend` — it establishes what implementing one correctly would need to get right, and where "just use Docker, it's namespaces too" would be a wrong assumption to carry over.

Writing it surfaced two live findings that were fixed on `NamespaceBackend` directly rather than only documented for later (CVE-2026-31431's `AF_ALG`/`AF_VSOCK` block, and the `socketcall(2)` multi-arch bypass check) — see reconciliation §§7–9 addenda. Those are done; this document is the comparison itself.

## 2. Isolation-guarantee-by-guarantee comparison

| Guarantee | `NamespaceBackend` (verified here) | Docker (documented) | Verdict |
|---|---|---|---|
| User namespace remapping | Always on — every run uses `unshare --user --map-root-user`. "Root" inside always maps to an unprivileged host UID, unconditionally, by construction. | **[Docker, documented]** `--userns-remap` is **off by default**. Without explicit daemon configuration, container root maps directly to host root (subject to the default capability drop and other mechanisms, but not user-namespace-isolated). | **NamespaceBackend is stricter.** A `DockerBackend` inheriting "Docker uses namespaces, so this is handled" would be wrong — it would need `--userns-remap` explicitly configured and verified, not assumed. |
| `no_new_privs` | Always on — `_ns_init.py` sets `PR_SET_NO_NEW_PRIVS` unconditionally before every exec. | **[Docker, documented]** Off by default (confirmed from CIS Docker Benchmark control 5.25 and Docker's own docs: *"by default, new privileges are not restricted"*). Requires `--security-opt=no-new-privileges` explicitly. | **NamespaceBackend is stricter.** Same pattern as user-namespace remapping: a default-off guarantee on Docker's side that must be explicitly requested, not assumed present. |
| cgroup resource limits | cgroup v1 memory + pids, verified adversarially: an oversized allocation is caught via `memory.failcnt` and reported `RESOURCE_EXCEEDED`; a fork bomb is stopped by `pids.max`. | **[Docker, documented]** Uses cgroups (v1 or v2 depending on host) for `--memory`/`--pids-limit` etc. — same underlying kernel mechanism, different API surface (CLI flags/daemon API vs. direct cgroup-filesystem writes here). | **Likely equivalent**, but not proven — the mechanism is the same primitive; the same adversarial tests (oversized allocation, fork bomb) need to be re-run against a real `docker run` before this can be called verified rather than assumed. |
| Filesystem jail | `chroot` into a workspace, minimal base rootfs bind-mounted read-only. Verified: absolute-symlink escape and relative path-traversal both stay contained. | **[Docker, documented]** OverlayFS + an image-derived root filesystem — architecturally different (image layers, not a bind-mounted host rootfs). | **Different mechanism, independent verification required.** The specific symlink/traversal adversarial tests that pass here say nothing about an OverlayFS-based filesystem's own escape surface — that needs its own test pass, not an inherited assumption. |
| Seccomp — overall philosophy | **Default-ALLOW** with a curated ~31-entry denylist (`_seccomp.py`). Small, auditable, intentionally not a claim of matching any reference profile. | **[Docker, documented]** **Default-DENY (`SCMP_ACT_ERRNO`)** allowlist — the [default profile](https://github.com/moby/profiles/blob/main/seccomp/default.json) explicitly allows several hundred syscalls and denies everything else. Structurally the *opposite* approach. | **Neither is simply "stricter."** A denylist can miss something dangerous that was never added; an allowlist can be safer by construction but is far more work to build and to keep from breaking legitimate workloads (see §3 below — Docker's own AF_ALG history is a case study in exactly this trade-off going wrong in both directions). A `DockerBackend` should not assume the denylist philosophy transfers — Docker's allowlist is the more defensible default *if* rebuilt correctly, not a lesser version of this one. |
| Seccomp — `AF_ALG`/`AF_VSOCK` (CVE-2026-31431) | Blocked via argument-conditioned `seccomp_rule_add_array()` on the native `socket` syscall, `SCMP_ACT_ERRNO(EPERM)`. Verified via a stand-in family (`AF_INET`) since `AF_ALG` doesn't resolve on this host at all. | **[Docker, documented]** Also blocked, via the identical mechanism in spirit (single `arg0 == 38 → SCMP_ACT_ERRNO` rule) — but with `errnoRet: 97` (`EAFNOSUPPORT`) specifically, not `EPERM`. Deliberate choice, per the merged PR's own review discussion: "`EAFNOSUPPORT` is the semantically correct errno... apps that probe for `AF_ALG` support will interpret it as 'not available here' rather than 'permission denied.'" | **Equivalent in outcome, a real (minor) difference in polish.** `NamespaceBackend` uses `EPERM` uniformly across its whole denylist rather than the more semantically precise `EAFNOSUPPORT` for this specific case — a small, legitimate refinement Docker's own review process caught that this branch's original CVE fix didn't. Worth adopting; tracked below, not silently left as "good enough." |
| Seccomp — `socketcall(2)` / multi-arch | Added to `DENIED_SYSCALLS` unconditionally (resolves to nothing on this host's native table, so it's a no-op here; would be a real block on a host where it resolves). Verified via a compiled int-`0x80` probe: blocked here — not by this rule, but by libseccomp's own kill-on-unrecognized-architecture safety net, since this filter never declares `x86`/`x32`. | **[Docker, documented] This is the important one.** Docker's *first* fix (PR #52501) took the same approach — block `socketcall(2)` outright — and it **shipped a regression**: it broke legitimate 32-bit programs and i386 container images, which use `socketcall` for entirely ordinary reasons, not just the exploit path. The follow-up fix (moby/moby#52537) **replaced the seccomp-level block with AppArmor (`deny network alg`) and SELinux (`alg_socket`) rules** — LSM hooks on `security_socket_create()`, which fire regardless of syscall entry point and can see the real address-family value (seccomp/BPF cannot dereference the userspace pointer `socketcall`'s real arguments live behind — this is a hard architectural limit of seccomp-bpf, not a bug in either implementation). | **This branch is carrying Docker's *already-superseded* mitigation, not its current one.** `NamespaceBackend`'s design (host-bind-mounted rootfs, not an image with packaged 32-bit binaries) makes the specific regression Docker hit less likely — but "less likely" was Docker's own assumption too, once. It has not been disproven here; no 32-bit binary has actually been run against this sandbox to check. AppArmor is not available in this build environment to even attempt the LSM-hook approach (`apparmor_parser` absent, `/sys/module/apparmor/parameters/enabled` missing — checked directly, not assumed). This is the single most important finding in this document: **not a Docker-vs-us comparison to resolve now, but a known, disclosed risk to carry forward, independent of whether a Docker backend is ever built.** |
| Network — deny-all | A network namespace with no configured route (`ENETUNREACH` to everything, verified). | **[Docker, documented]** `--network none`, or an internal bridge network with no gateway — same structural guarantee (no route out), different configuration surface. | **Equivalent**, pending the same kind of direct adversarial re-verification (connect attempt, confirm the specific errno) rather than assumed from the config option's name. |
| Network — `allowed_hosts` (DEBT-023) | A **custom mechanism specific to this backend**: named netns + veth pair + a purpose-built stdlib HTTP(S)-CONNECT proxy (`_net_proxy.py`) on the host-side peer, `HTTP_PROXY`/`HTTPS_PROXY` injected into the sandbox's environment. HTTP(S)-only — a raw non-HTTP TCP/UDP connection to an "allowed" host is still blocked. | Docker has no equivalent first-class concept — `docker run` doesn't take an `--allowed-hosts` flag. A `DockerBackend` supporting `allowed_hosts` would need to build the *same kind of thing this branch already built*: a container on an isolated Docker network with no default route out except to a proxy, `HTTP_PROXY`/`HTTPS_PROXY` set via `-e`. | **Not a Docker feature to inherit — a mechanism to reuse.** `_net_proxy.py` itself is backend-agnostic (it's a plain host-side TCP listener; nothing about it is namespace-specific). A `DockerBackend` implementing `allowed_hosts` should very plausibly point a container at this *same* proxy process rather than build a second one — genuine potential for code reuse across backends, not duplicated work. |

## 3. The three things asked about directly

**Does Docker's profile block `AF_ALG`/other dangerous socket families?** Yes, as of the CVE-2026-31431 response (`moby/profiles#20`, merged April 30, 2026, vendored into `moby/moby` via PR #52501/#52494). Before that, `AF_ALG` was allowed by the socket rule; only `AF_VSOCK` was denied. The fix is *not* a general "dangerous families" sweep — it's targeted at the two families implicated in this specific CVE. Nothing found in the sources reviewed here suggests Docker's default profile blocks other exotic families (e.g. `AF_XDP`, `AF_TIPC`) by the same mechanism; that would need its own investigation if it mattered for this project, not an assumption piggybacked on this one fix.

**How is the argument filtering expressed?** Docker's seccomp profiles are JSON (`moby/profiles/seccomp/default.json`), with per-rule `"args"` arrays of `{"index", "value", "op"}` objects compiled by `runc`/libseccomp into the same BPF program structure `NamespaceBackend` builds directly via ctypes. The actual merged rule for `AF_ALG`:

```json
{
  "names": ["socket"],
  "action": "SCMP_ACT_ERRNO",
  "errnoRet": 97,
  "args": [{ "index": 0, "value": 38, "op": "SCMP_CMP_EQ" }]
}
```

This is structurally identical to what `_seccomp.py` builds via `seccomp_rule_add_array()` — same syscall, same argument index, same comparison, same value, different declared errno (see §2's table row). The two implementations reach the same libseccomp primitives from different starting points (JSON compiled by `runc`, vs. ctypes calling libseccomp directly here) but express the *rule itself* almost identically. Docker's own history is also the source of a real, general lesson worth stating plainly: their maintainers found that combining a **second** `!=` condition on the *same* argument index into an *existing* allow-rule doesn't reliably work in libseccomp, and that layering a separate deny-rule on top of an existing broader allow-rule for the same syscall+argument doesn't reliably win either, because of first-match-wins evaluation order. `NamespaceBackend` doesn't hit this specific failure mode — its baseline policy is default-ALLOW with no pre-existing rule on `socket`'s arguments to conflict with — but the general principle (test the *actual* rule-combination behavior, don't assume argument conditions compose the way plain boolean logic would suggest) is exactly why this document verifies rather than asserts throughout.

**Stricter, equivalent, or capability-driven exceptions?** All three, depending on the dimension — deliberately not one verdict:
- **Stricter:** user-namespace remapping and `no_new_privs`, both always-on here vs. default-off on Docker.
- **Equivalent, pending re-verification:** cgroups, network deny-all, the `AF_ALG`/`AF_VSOCK` block itself.
- **Behind, in a way that matters:** the `socketcall`/multi-arch mitigation — this branch still relies on Docker's *first, superseded* fix, not their current one, and doesn't have AppArmor/SELinux available in this environment to close that gap the way Docker ultimately did.
- **Capability-driven exception, no Docker analog:** DEBT-023's `allowed_hosts`. This is exactly what `RuntimeCapabilities`/`AdmissionGate` (reconciliation §3's naming decision) were built for — a `DockerBackend` would declare its *own* `RuntimeCapabilities` honestly (very plausibly *not* including `NETWORK_ALLOWLIST` on day one, even once user-namespace remapping and `no_new_privs` are configured and verified), and `AdmissionGate` would correctly refuse an `allowed_hosts` request against it until the proxy-reuse approach in §2's last row is actually built and tested — the same fail-closed behavior that already protects `StubBackend` from being mistaken for something it isn't.

## 4. What a `DockerBackend` implementation must independently verify, not inherit

In priority order, matching what this document found rather than a generic checklist:

1. **`--userns-remap` configured and verified** — not merely present in a config file, but adversarially confirmed the same way `NamespaceBackend`'s mapped-root was (attempt something that would require real root, confirm it fails).
2. **`--security-opt=no-new-privileges` set explicitly** — Docker's default is off; this needs to be a deliberate `DockerBackend` choice, not an inherited assumption.
3. **The `socketcall`/multi-arch question resolved, not carried forward unresolved a second time.** Either: confirm (via the same int-`0x80` technique used here) that a Docker container without AppArmor/SELinux available is *actually* exposed to this bypass before assuming otherwise, or get AppArmor/SELinux LSM rules working and verified on whatever host runs this. Do not ship a `DockerBackend` that quietly relies on the same superseded seccomp-only mitigation this document just flagged as insufficient.
4. **Filesystem escape tests re-run against the real OverlayFS-backed filesystem** — the symlink/traversal tests that pass here are informative about the *category* of test needed, not evidence about Docker's differently-constructed filesystem.
5. **cgroup limit enforcement re-run** — same adversarial pattern (oversized allocation, fork bomb), against real `docker run` limits.
6. **`AF_ALG`/`AF_VSOCK` handling confirmed present on whatever Docker version is actually deployed** — this is a 2026 fix; an older pinned Docker version would not have it, and `DockerBackend` should not assume a CVE fix landed in the specific version in use without checking.
7. **`errnoRet: 97` (`EAFNOSUPPORT`) adopted for the `AF_ALG` rule in `_seccomp.py` itself**, independent of the Docker backend question — this is a small, standalone correctness improvement to `NamespaceBackend` that this comparison surfaced and that doesn't need to wait for step 3 at all.
8. **`_net_proxy.py` reuse evaluated concretely** once `allowed_hosts` support is attempted for Docker — check whether pointing a container's `HTTP_PROXY`/`HTTPS_PROXY` at the existing proxy process, on an isolated Docker network with no other route out, actually works end-to-end the way it does for `NamespaceBackend`, rather than assuming the mechanism ports cleanly just because the proxy itself is backend-agnostic.

None of the above is implemented by this document. It is the explicit backend-security comparison the sequence called for — the gate step 3 needs to pass through, not step 3 itself.
