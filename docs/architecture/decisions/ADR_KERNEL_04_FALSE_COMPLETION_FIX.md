# ADR-KERNEL-04: False Completion Fix (DEBT-020) — Kernel v1.0 Freeze Blocker

**Status:** Accepted
**Date:** September 6, 2026
**Context:** `docs/Bugs Hunt & fix reports/FALSE_COMPLETION_KERNEL_AUDIT_PRE_IMPLEMENTATION_REPORT.md` (Sept 2, 2026) traced a live path where a workflow node completing without error is reported as `success=True` regardless of whether the output actually satisfied the request's stated constraints. `docs/studies/OCBRAIN_KERNEL_V1_FREEZE_AUDIT_SEPT_2026.md` (Sept 6) independently re-verified every claim against current `main` and classified the Kernel `NOT_FREEZE_READY` solely on this item, per both reports' explicit deferral of the blocker-or-not decision to the project owner. Moncif's decision: **DEBT-020 is a Kernel v1.0 freeze blocker** — "successful completion must mean the requested task actually satisfied its applicable constraints" — with remediation scoped to exactly three points, explicitly excluding resumability, generalized coverage infrastructure, continuous verification, and the Verification/Critic/Evidence branch.

---

## What tracing this fix found, beyond what either prior report established

The Sept 2 report flagged three items as **OPEN — next thing to trace** before implementation could safely start. All three were closed here, by direct code reading, not assumption:

1. **Where does `WorkflowRuntime`'s return value become literal response text?** `core/orchestrator.py`, `Orchestrator.handle()`, line 461 (K4.2 branch): `answer = wf_result.output or ""`, used completely unconditionally — `wf_result.success` was never read on this branch at all, for any reason, before this fix. This matters independently of DEBT-020's specific constraint-checking angle: even a `WorkflowResult.success=False` from a *genuine* node error was already being silently ignored here before this fix, and remains so after it (see "What was explicitly not done" — not pulling that in was a deliberate scoping choice, not an oversight).

2. **Does `Constraint` survive past extraction into anything `WorkflowDefinition` can see?** No — and this is a more complete gap than either prior report characterized. `_extract_constraints()`'s output is used transiently inside `Planner.plan()` for `_sequence()`/`_justify()`/`check_precheck_rejection()`, then the `ExecutionPlan(...)` constructor call is reached — and `ExecutionPlan` has **no `constraints` field at all**, so the list simply falls out of scope. `compiler.compile()`'s `WorkflowDefinition(...)` call likewise had no field to receive anything. Fixing this required more than the report's finding #1 ("Constraint has no quantitative field") implied: even a perfectly quantitative `Constraint` would have had nowhere to go.

3. **Does `execution_outcome.py`'s `is_success` conflation actually feed the K4.2/WorkflowRuntime success path the report's finding #2 and finding #4 read as connected?** Traced the full chain: `core/workers/capability_executor.py`'s `CapabilityExecutorWorker` (the live K4.2 default worker) calls `AdapterRuntime.invoke()`, not `model_router.route()`. `AdapterRuntime.invoke()` determines its own `success`/`CapabilityResult` independently and never reads `execution_detail`. The only real production call site that constructs an `ExecutionOutcome` (`model_router.py`'s `_call_monitored_streaming`) never actually produces `FailureType.COMPLETED_WITH_PARTIAL_OUTPUT` in practice (its branches only ever yield `SUCCESS`/`PROVIDER_FAILURE`/`STALLED`/`HARD_DEADLINE`/`EMPTY_RESPONSE`). `execution_detail`/`is_success` is read only by `validate_live.py` (a manual diagnostic script) and this session's own tests. **Correction to the record:** this specific conflation is real but isolated to `model_router.py`'s `stream_route()` — the `interface/api.py` streaming-endpoint bypass, `KNOWN_ISSUES.md` DEBT-017 — not a mechanism actively feeding the WorkflowRuntime/Orchestrator false-success path this fix's other two parts target. Fixed anyway (see Part C) because it is explicitly named in the approved scope and is a live hazard for whichever future integration eventually does wire `execution_detail` into a success decision.

## Part A: Constraint gets an actual checkable value (scope point 1)

`core/cognitive/planner.py`'s `Constraint` dataclass gains `measure: Optional[str]`, `comparator: Optional[str]`, `target: Optional[float]`, `is_measurable() -> bool`, and `is_satisfied_by(actual: float) -> bool`. General shape (not word-count-specific) so item-count and file-coverage constraints could instantiate it later without a redesign — per the originating report's own "IMPORTANT DISTINCTION." Only word-count extraction is implemented (`_extract_word_count_constraints`, new patterns for "at least/at most/exactly/more than/fewer than N words" plus a bare "N words" fallback read as a floor, not an exact target) — the demonstrated bug case. Item-count/file-coverage extraction is explicitly not attempted (see "What was explicitly not done").

A checkable-but-unpopulated field would have been exactly as inert as the pre-existing `COMPLETED_WITH_PARTIAL_OUTPUT` gap (Part C) — extraction had to be part of "make constraints concretely checkable," not just the data model, or point 3 would have nothing real to check against.

## Part B: constraints threaded through to where they can be checked (scope point 3, data-flow half)

`ExecutionPlan` (core/cognitive/planner.py) and `WorkflowDefinition` (core/workflow/definition.py) both gain `constraints: List[Constraint] = field(default_factory=list)`, populated at construction in `Planner.plan()` and `compiler.compile()` respectively — mirroring `root_operation_id`'s own precedent from `ADR-KERNEL-01` exactly, including the same "None/empty for anything built outside the cognitive pipeline" default behavior. This also **closes `ADR-KERNEL-01`'s own I7 question a second, unrelated way**: `WorkflowDefinition`'s docstring carried a stale copy of the "revisit if DEBT-003 changes this" note that had already been resolved in the ADR file itself during `ADR-KERNEL-03` but never mirrored here — corrected in place while this docstring was already being touched, not left dangling.

## Part C: success distinguishes complete from partial/non-conforming (scope point 2)

Two independent additions, since tracing found two independent instances of the underlying pattern:

1. **`WorkflowResult` gains `constraint_violations: List[str]`.** `WorkflowRuntime._run()`, after computing `success` from node-level outcomes exactly as before, adds one further check (`_check_constraints`, a pure function, directly unit-testable, matching `watchdog_decision.decide()`'s established shape in this codebase): if `success` is still `True` and `definition.constraints` contains a measurable `HARD` constraint the final output fails, `success` becomes `False` and the violation is recorded. `SOFT` constraint violations are advisory only — the same HARD/SOFT distinction `_detect_contradictions` (`core/cognitive/planner.py`) already applies elsewhere. A genuine node error is never re-examined for constraint satisfaction — checking data that was never meant to be the final answer would be meaningless, and the existing error message must not be overwritten by an unrelated constraint description.
2. **`core/runtime/execution_outcome.py` gains `is_fully_satisfied`**, `True` only for `FailureType.SUCCESS` — `is_success` (existing, zero production callers, left unchanged in meaning) still answers "produced usable output" for whichever future caller wants that weaker question. See "What tracing found" §3 for the honest account of what this currently does and doesn't connect to.

## Part D: the check runs before the response is accepted (scope point 3, enforcement half)

`core/orchestrator.py`, `Orchestrator.handle()`'s K4.2 branch: after `wf_result` comes back, `wf_result.constraint_violations` is checked before `answer` is treated as final. On a violation, the output is **kept, not discarded** — partial work usually still has real value to the person who asked — but an honest disclosure is appended (`"(Note: this response may not fully satisfy your request -- ...)"`), and `orchestrator.response_incomplete` is emitted for observability. This is the literal "final response acceptance" point scope-point-3 names.

## What was explicitly not done

- **Resumability, generalized coverage infrastructure, continuous verification, the Verification/Critic/Evidence branch** — per Moncif's explicit instruction. Nothing here touches `core/verification/`, the `feature/verification-critic-evidence-phase-c` branch, or `WorkflowRuntime.resume()` (`ADR-KERNEL-03`); constraint-checking is independent of and does not interact with resume's own node-skip logic (a resumed node's cached, already-checked result is not re-checked against constraints a second time, since it was already checked — or not subject to any — the first time it completed).
- **Item-count and file-coverage extraction.** The data model (Part A) supports them; no extractor exists yet. Future work, not attempted.
- **The K4.2 branch's total absence of genuine-node-error handling** (`wf_result.success == False` with no `constraint_violations` was, and remains, silently un-checked at line 461/`answer = wf_result.output or ""`). Found while tracing item 1 above. Real, but a different, pre-existing gap this fix's explicit three-point scope does not cover — flagging it rather than silently folding an unrelated fix into this one.
- **`stream_route()`/`interface/api.py`'s streaming bypass** (`DEBT-017`) is unaffected. `is_fully_satisfied` (Part C.2) exists for whenever that gets addressed; nothing here wires it in.
- **The legacy K2.2 fallback path** (`Orchestrator.handle()`'s other `WorkflowRuntime.execute()` call site, ~line 601, `build_planner_workflow()`) has no `ExecutionPlan`/`Constraint` machinery available to it at all — a single generic `PlannerWorker` node, not the K4.2 Constraint-aware pipeline. Not retrofitted; this path is only reachable when `use_k42_frontend=false`, an increasingly vestigial configuration since that flag defaulted to `true` on Aug 28, 2026.

## Evidence

`tests/test_debt_020_false_completion.py` (new, 37 tests): `Constraint.is_measurable()`/`is_satisfied_by()` across every comparator and exact boundary values; word-count extraction across every qualifier phrasing plus overlap-safety (a qualified phrase does not also match the bare fallback and double-count); the pure `_check_constraints` function across satisfied/violated/soft-not-enforced/unmeasurable-skipped/unsupported-measure-skipped/non-string-output-skipped/mixed-constraints cases; and five `WorkflowRuntime.execute()` end-to-end tests (satisfied → success; violated → failure with output preserved; soft violation → still success; no constraints → unchanged from before this fix; genuine node error → not relabeled as a constraint violation). `tests/test_integration_full_pipeline.py` (2 new tests, `TestConstraintsSurviveRealPipeline`): a word-count phrase survives the **real** `interpret_request() -> plan() -> compile()` pipeline (not a hand-built fixture) and lands on the compiled `WorkflowDefinition` as an actually-measurable constraint; a request naming no quantity produces none.

Full suite: 1,406 passed / 39 failed (34 pre-existing environmental — `huggingface.co` unreachable in this sandbox, confirmed by direct isolation earlier this session and reconfirmed unrelated to this fix by running `test_planner_worker.py` against the pre-fix commit and observing the identical failure count — plus the 5 pre-existing intentionally-red security-regression tests, DEBT-019, unchanged). Zero regressions. 39 new tests.

## Consequences

- DEBT-020 (`KNOWN_ISSUES.md`) is resolved by this ADR.
- `WorkflowResult.success`'s meaning has changed for any `WorkflowDefinition` that carries constraints: it now also requires measurable-hard-constraint satisfaction, not just node-level non-error. No existing test or caller is affected, since no `WorkflowDefinition` before this fix ever had a non-empty `constraints` list.
- Per Moncif's stated sequence, next: full suite (done, above) → **fresh freeze audit** → debt/register reconciliation → freeze decision → Hail-Mary reliability campaign.
