## 3. Findings → OCBrain architectural implications

**3.1 Self-correction without external grounding is unreliable.** Research on Reflexion's limitations: LLMs "often fail to correct reasoning errors reliably without external validation signals, and their performance can even decrease after attempting to self-correct... The primary bottleneck lies in error detection rather than error correction" (Huang et al. 2024; Tyen et al. 2024, as summarized in arXiv:2604.06066). CRITIC's own conclusion is the positive complement: tool-interactive, externally-grounded critique reliably improves outputs where pure self-verification does not (arXiv:2305.11738). *Implication:* the mission's deterministic-first rule (§31) and its skepticism of model self-report (§53) aren't just caution — they're the documented failure mode. Any verifier design that leans on the same model reflecting on its own output, without an external check, is building on the weakest link in the literature.

**3.2 "False success" in agents is now a named, measured, current phenomenon.** "From Confident Closing to Silent Failure: Characterizing False Success in LLM Agents" (arXiv:2606.09863, June 2026) built false-success detectors on tau2-bench and AppWorld. Finding: some agent architectures "always write status=success on completion regardless of outcome, making their status field uninformative as a self-assessment signal" — measured false-success rates as high as 75.8% for those architectures. Cross-domain detector transfer without calibration is weak (AUROC ~0.69) but improves substantially with 50–100 labeled examples per class (AUROC 0.79–0.83). Separately, current industry practice converges on the same answer: "the pattern across the serious benchmarks is execution-based verification... verify the end state, not the last message" (morphllm.com, AI Agent Evaluation 2026). *Implication:* this is direct, dated validation of flagging `EvaluatorWorker`'s caller-supplied-parameter fallback (Phase A finding) as the exact anti-pattern to close. It also suggests a concrete deterministic verification method worth building: a trained/calibrated false-success classifier over trajectory features, not just an LLM asked "did this succeed?"

**3.3 Exact source attribution is a harder, separate problem from generic support-checking.** ProvenanceGuard (arXiv:2606.18037, July 2026) names the failure mode directly: "an answer can be broadly supported by retrieved material while still attributing the claim to the wrong source" — cross-source conflation. Their numbers make the gap concrete: block/reject F1 of 0.846 on a hard multi-source benchmark, while source-plus-relation accuracy on the same benchmark drops to 0.229. A June 2026 survey ("From Agent Traces to Trust: Evidence Tracing and Execution Provenance in LLM Agents," arXiv:2606.04990) maps almost directly onto the mission's §14–27 evidence/provenance model and is worth reading in full before finalizing that section. *Implication:* strong, current, quantified support for the mission's §15 exact-evidence-binding requirement — general "is this supported" checks will pass things that are attributed to the wrong source, silently.

**3.4 Verifiers are not reliable by default and must be evaluated as their own component.** The largest current study of LLM-as-judge reliability (arXiv:2606.19544, June 2026; 21 judges, 9 providers, ~541,000 judgments) found "high test–retest reliability (>0.95) coexists with severe position bias (>0.10)" in production-deployed judges — a judge can be internally consistent and systematically wrong at the same time. RAND's Judge Reliability Harness (March 2026) reports frontier models exceeding 50% error rates on hard bias benchmarks and that "no judge was uniformly reliable" across tasks. *Implication:* concrete, dated backing for §81 (verifier meta-evaluation) as non-optional. A verifier that agrees with itself consistently has told you nothing about whether it's right.

**3.5 The current real-world pattern is multiple narrow verifiers, not one judge.** Microsoft's FaraGen1.5 pipeline scores every agent trajectory with three separate, purpose-built verifiers: "the Alignment Verifier checks if the trajectory of actions match the task's intent; the Rubric Verifier defines completion criteria and scores the trajectory against them; and the Multimodal Verifier reviews screenshots and responses to confirm visual evidence supports successful completion" (Microsoft Research, Fara-7B blog). Their "Universal Verifier" (internally MMRubricAgent) and the accompanying CUAVerifierBench are explicitly built to measure "both process and outcome rewards" (arXiv:2604.06240) — the same process/outcome split the mission requires in §12. Separately, RuVerBench (arXiv:2606.29920, June 2026) reports rubric-verification reliability by category (Facts/Format/Logic/Numbers for research tasks; Task/Rules/Planning/Tools for agentic coding) rather than one aggregate score. *Implication:* both of the mission's most structurally demanding rules — multiple independent verifier types per target, and never collapsing results into one number — have concrete, shipped, 2026 precedent, not just theoretical justification.

**3.6 Security: evidence-as-instruction is a live, unresolved threat, not a theoretical one.** AgentDojo remains the standard indirect-prompt-injection benchmark (97 tasks, 629 security cases). Published results still show real attack success against undefended tool-using agents — utility drops under attack even for strong models, and targeted attack-success rates are non-trivial on canonical attack templates. *Implication:* §56/§92's "evidence is data, never instruction" boundary needs to be enforced structurally (parsing/sanitization before evidence ever reaches a reasoning context), not just stated as a policy, given how well-documented successful injection still is in 2026.

## 4. Two explicit decisions the corrective doc required (§39, §40)

**§39 — EvaluatorWorker disposition: (A), with a specific fix.** `EvaluatorWorker` should remain a real, narrow, measurement-only component for the event-grounded case — its stated invariant ("evaluation never changes facts") and scope ("what happened, not why") are already correctly aligned with one slice of what the mission wants. The new Verification System should become the independent subsystem, and should specifically supersede `EvaluatorWorker`'s caller-supplied-parameter fallback path: "no runtime event exists yet" should never again silently mean "trust what the caller says" (finding 3.2 above). That path should become an explicit `INSUFFICIENT_EVIDENCE` finding instead. This is a recommendation from a ~45-line partial read of a 297-line file — worth confirming against the full implementation before committing.

**§40 — GraphRAG Evidence disposition: KEEP + WRAP.** `graphrag.Evidence` already carries genuine, narrow provenance (`retrieval_method`, source `KnowledgeEntry`) worth preserving, but it was never meant to cover tool results, runtime state, or external citations — and finding 3.3 above (attribution is genuinely harder than generic support) means the new canonical `EvidenceItem` model needs real source-binding machinery GraphRAG's retrieval-scoped design doesn't attempt. Recommend treating `graphrag.Evidence` as one concrete `EvidenceSource`/`EvidenceObservation` implementation the new model wraps, not a class to replace or a name to reuse for something broader.
