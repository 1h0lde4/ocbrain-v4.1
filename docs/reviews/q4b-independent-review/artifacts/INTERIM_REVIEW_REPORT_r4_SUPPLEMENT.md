## 1. Package A: hard-deadline topology (observation only; no asyncio task cancellation was used, so no #105 contract is tested; #105 lists "watchdog only sets the token" as its own related gap, so this matrix is evidence about it, not a competing test)
Setup (rev_probe_g, on `2491ae4`): budget hard ceiling 1 s; workers sleep 2.5 s without polling, or poll `context.cancellation_token.is_cancelled`. (A worker can poll the workflow token: `ExecutionContext.cancellation_token` is the workflow's token; `worker.cancel()` has no production caller.) Same evidence surfaces for every case.
| Case | WorkflowResult | Node results | Graph | Last checkpoint | Event history around the deadline |
|---|---|---|---|---|---|
| T1 single node, ignores token | success=True, error "" | a ok | root, a completed | a completed | `node.failed[root]`, `node.failed[a]`, then `node.completed[a]`, `completed[root]`, `workflow.completed ok=True` |
| T3 final node of a->b, ignores token | success=True, error "" | a, b ok | all completed | a, b completed | `node.failed[b]` then `node.completed[b]`, `workflow.completed ok=True` |
| T5 non-final a of a->b, ignores token | success=False, "Workflow cancelled" | a ok | root failed, a completed, b pending | a completed, b pending | `node.failed[a]`, `node.completed[a]`, `execution.failed`, `workflow.completed ok=False` |
| T7 middle b of a->b->c, ignores token | success=False, "Workflow cancelled" | a, b ok | root failed, c pending | c pending | same pattern |
| T2/T4/T6 node polls token | success=False, error = the worker's own text | polling node failed | failed (successors pending) | failed | `node.failed` then `execution.failed`; no event or field says "deadline" |
Token is cancelled in every case; no task is left running. Observed, separated from any decision:
- Q1 (does the watchdog enforce a hard deadline?): in this runtime it only cancels the token and marks graph nodes failed; it does not stop a node that ignores it.
- Q2 (what must workflow status represent at expiry?): the same expired deadline yields success (ignoring final node), "Workflow cancelled" (ignoring non-final node) or the worker's own failure text (polling node), and the deadline event `node.failed` is later followed by `node.completed`. The outcome depends on DAG position and worker cooperation, not on the deadline. No `cancelled` workflow status exists.
- OWNER DECISION, not made here: which surface is authoritative at a deadline, and the #105 contract. UNRESOLVED.
Not run (reserved to #105): asyncio cancellation during execution, during retry backoff, and after several completed nodes; earlier S1-S3 (r2) remain the only observations of cancel-then-resume.

## 2. Package B: persistence and the missing commit boundary
Observed order (K1-K5, F-15 sweep): worker runs -> result held in memory -> `execution.node.completed` event -> checkpoint -> next node; no transaction spans them. Five separate facts, mapped to evidence:
| Fact | Where it can diverge (evidence) |
|---|---|
| Work performed | F-15 `node.completed` event failure: node ran, workflow reports failure (rev_probe_a2 i=7). K3: node b completed before a hard exit and was run again |
| Result in memory | lost when `execute()` raises (F-15 root-status failure) |
| Result in event history | restore replays synthetic `execution.node.completed` ("Restored from checkpoint"): a=3 completions in K5 while a ran once; counts are not execution counts. Orphan `worker.started` without terminal event after a kill |
| Recovery state persisted | K1 healed by later checkpoint; K2 none; K3/K4 stale |
| Result communicated | F-15 root-status failure: `execute()` raises OSError after the node ran and its checkpoint was saved (a2: raised OSError, 1 checkpoint). The exception carries no `instance_id`, and the only way to find it is scanning the event store (done in S3 and K-runs). `resume()` has no production caller |
Combination check of the supplied table: (completed, event failed, no checkpoint), (completed, event ok, checkpoint failed), (all ok) and (completed, final lifecycle event failed, checkpoint ok -> exception, no instance id) are each reproduced (a2 i=7; K1/K2; baseline; a2 i=8). Reported success can be wrong in both directions: false success (T1/T3, K2) and false failure (F-15 i=7).
`EventStream` event ids: PARTIALLY VERIFIED. `StreamEvent.event_id` defaults to a fresh uuid4; the table has `event_id TEXT UNIQUE NOT NULL`; the store's `append(event)` has no `IntegrityError` handling and no idempotent-append behavior; no production caller-supplied id was found (grep, not exhaustive). The event log is therefore not an authoritative attempt history on its own. No schema change is proposed.
