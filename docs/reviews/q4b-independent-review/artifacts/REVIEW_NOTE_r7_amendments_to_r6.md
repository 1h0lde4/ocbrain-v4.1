## 1. `interaction_id` is a deterministic query key (amendment 1)
`_interaction_id(query)` returns `"interaction:" + sha256(query)[:32]` (`orchestrator.py` ~44-68) and the same value is passed to `WorkflowRuntime` as `session_id` (~528, ~718). Probe K1 (K4.2 stack, three concurrent requests: same text, same text, different text): 3 requests, 2 distinct ids; the two identical requests share one. The `FZ-06` register row already documents this ("SHA-256 of the query text, so identical queries share it"), so this clarifies FZ-06 and is not a new finding. Consequence: `orchestrator.query_started/completed` cannot tell concurrent identical requests apart. r6's description of `interaction_id` as an identity domain is amended to "query key, not an interaction instance id".

## 2. The Brain API is mounted and has its own identity behavior (amendment 2)
Mount chain (source): `main.py` ~420-422 `api_setup(orchestrator, scheduler)` -> `interface/api.py` ~101-102 `register_brain_api(app, ...)` -> `core/brain_api.py` ~171 `include_router(router)`; route `POST /brain/v2/query` (`APIRouter(prefix="/brain/v2")`) takes a body with only `query` and calls `orch.handle(req.query)` (~122) with no `execution_id`; a second `handle()` call sits in a helper (~181, not exercised). `WorkflowRuntime` then uses `execution_id = metadata.execution_id or instance_id` (`runtime.py` ~484). Probe K2 (real FastAPI app, both routes): `POST /query` with a client `execution_id` -> events carry `execution_id = CLIENT-X` and a different `instance_id`; `POST /brain/v2/query` -> `execution_id == instance_id` (same value). So r6's "no durable execution <-> instance mapping" is route-specific: it holds when a caller supplies an `execution_id` (the primary `/query` route always does, client-supplied or generated); on `/brain/v2/query` the two collapse into one value. r6 s1 item 6 ("whether that app is mounted in production was not determined") is replaced by: mounted, and exercised via ASGI (not a real server).

## 3. Caller inventory (amendment 3)

## 4. Two separate `root_operation_id` / identity-loss boundaries (amendment 4)
(a) `WorkflowDefinition` -> run metadata / `ExecutionContext` / events / checkpoint: `core/workflow/runtime.py` has 0 references to `root_operation_id`; probe F on `2491ae4` (definition built with `root_operation_id="ROOT-OP-1"`) shows it absent from worker context metadata and from every event. On the K4.2 path it is persisted only in `cognitive.plan_compiled` and is reachable from runtime events only by joining on `workflow_id`. (b) `CapabilityExecutorWorker` -> `CapabilityRequest` (r6 item 3): the worker has `request_id`, `execution_id`, `instance_id`, `attempt_id` in its context and forwards none; it never had `root_operation_id`, because of (a). (a) breaks the logical-operation lineage before any worker exists; (b) is the immediate cause of the capability `trace_id` mismatch. Both remain under FZ-06/DEBT-030; no new debt.

## 6. Fake-adapter evidence vs the production adapter (amendment 6)
Production registers `ModelRouterAdapter(model_router)` first for `LLM_COMPLETION` (`main.py` ~283). Probe K3 therefore installs the REAL `ModelRouterAdapter` over a fake `ModelRouter`. Methodology: the first run was INVALID (the registry appends adapters in priority order, so the fixture's fake adapter still handled the call; kept as `out_rev_k_probe_run1_K3_INVALID_adapter_not_replaced.json`); the rerun clears the fake from the private `_adapters` list (reviewer-side) and records the registered adapter names. Result (rerun): router raising `RuntimeError`, and router returning `ExecutionOutcome(PROVIDER_FAILURE)`, both give a failed capability worker, `workflow.completed success=False`, `orchestrator.query_completed outcome="success"`, and HTTP 200 / `success: true` / empty answer; a normal router answer gives success everywhere. So at `2491ae4` the adapter-level failure mapping (FZ-02 B2a) works for these inputs, while the orchestrator-level outcome reporting (FZ-01) still reports success: two different findings, one fixed and one open. Not exercised: the real `ModelRouter`/provider and network, a real server, `main.py` composition. Observation only: `ExecutionOutcome` has its own `execution_id` field (router-level); its relation to the API `execution_id` was not examined.
