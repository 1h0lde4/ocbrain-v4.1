# OCBrain Q4-b review note r6: identity corrections to r5

**INTERIM. Evidence only, read-only, no remediation, no PASS, mission not closed.** Baseline `main` `2491ae469edd`. r1-r5 are untouched; r6 supersedes r5 s3 and part of its s2. Every item below was re-checked against recorded events or source, not taken from the critique on trust.

## 1. Corrections, in the order requested
1. **Invalid inference withdrawn.** r5 said `request_id` joins `execution.completed` "which carries `execution_id`", so `execution_id` and `instance_id` are derivable via `request_id`. Wrong: two different producers share the event name. Worker-level records come from `ExecutionRuntime` (`core/runtime/execution_runtime.py` ~211) with keys `duration_ms, error, request_id, success, worker_id, worker_type`. Workflow-level records come from `WorkflowRuntime` (`core/workflow/runtime.py` ~640, `execution.completed` or `execution.failed`) with keys `execution_id, node_id, status, summary`. In the J1 run, 6 records are the first schema and 2 the second; none carries both ids (outputs/out_rev_j1_execution_completed_records.txt, out_rev_j3.txt). The positional `node_id` ("step-N", `planner.py` ~1301) is reused across instances and is not a safe join key. Result: no persisted join between `execution_id` and `instance_id` or `request_id` was found.
2. **In-memory vs persisted.** In memory: `WorkflowResult` carries `workflow_id`, `instance_id` and `metadata["execution_id"]` (`runtime.py` ~667-668). Persisted: `cognitive.*` (`trace_id`, `operation_id`, `root_operation_id` only on `plan_compiled`, `workflow_id`), `workflow.*` and `system.checkpoint` (`workflow_id`, `instance_id`; checkpoint also nested `request_id`/`attempt_id`), `worker.*` (`task_id`, `worker_id`, `workflow_id`; `task_id` is the context `request_id`), `execution.node.*` and workflow-level `execution.*` (`execution_id`, `node_id`), `orchestrator.query_started/completed` (`interaction_id` only; `completed` adds `outcome`, `execution_path`), `adapter.invoked` (capability `trace_id` only). The Orchestrator receives the in-memory tuple and persists none of it. So the external-execution <-> instance mapping exists in memory and is not durably reconstructable from the event history. `interaction_id` is a further identity domain my earlier tables omitted (the J1 whitelist missed it); it has no persisted join to the others.
3. **Identity-loss boundary.** `CapabilityExecutorWorker` (`core/workers/capability_executor.py` ~116-123) holds `context.request_id` and `context.metadata` (`execution_id`, `instance_id`, `attempt_id`, `node_id`, `node_config`) but builds `CapabilityRequest(capability_type, payload={...})` with none of them; `CapabilityRequest.trace_id` then defaults to a fresh uuid4 and `AdapterRuntime` emits it in `adapter.invoked`. J1b confirmed the emitted id differs from the ambient trace id. The legacy planner bridge (`planner.py` ~321) behaves the same. This sharpens DEBT-030/FZ-06; it is not a second debt, and the same field name `trace_id` denotes two different identities.
4. **Dual `execution.completed` schemas.** Documented in item 1. Event `source` also differs (`ExecutionRuntime` vs `WorkflowRuntime`). Consumers cannot assume one identity schema for the event name and must discriminate by source or payload keys. Whether any production consumer relies on the name alone was not audited (the execution registry routes by payload `execution_id`, so worker-level records have nothing to route on).
5. **Operation-id semantics preserved (ADR-K4.2-H-08).** J4: `constraints_extracted` and `capabilities_discovered` share one `operation_id` and differ by `stage_tag` (`constraint_extraction`, `capability_discovery:<subgoal>:<n>`); `plan_compiled` has a separate `operation_id` and is the only event carrying `root_operation_id` (plan-stage events show `root_operation_id` None in this run, so the plan stages and the compiled plan are joined by the ambient `trace_id`). My earlier "different value per stage" was imprecise; this is intended behavior, not a defect. The J1 whitelist omitted `stage_tag`; J4 shows it.
6. **HTTP vs other callers.** Verified: HTTP through `interface/api.py` (J2: 4 requests, 4 distinct trace ids, one `httpx.AsyncClient` session). Same-task reuse (two `handle()` calls shared one trace id, J1); `get_trace_id()` creates and keeps the value and nothing in `tracer.py` resets it. Callers of `Orchestrator.handle()` found by grep: `interface/api.py` and `core/brain_api.py` (lines ~122 and ~181, no `execution_id` passed; whether that app is mounted in production was not determined). No scheduler or CLI call to `handle()` was found (the CLI is an HTTP client), so r5's reference to scheduler/CLI callers was speculative and is withdrawn as a gap; `main.py` has no trace initialization before `uvicorn.Server` (grep). Untested: `brain_api.py`, real startup context.
7. **FZ-01 retained as an existing debt, with production-path evidence, not recounted.** `orchestrator.py` K4.2 branch (~525-566, ~652-654): after `execute()` only `constraint_violations` is checked, `orchestrator.query_completed` is emitted with `outcome: "success"`, and a source comment (~537-552) states `wf_result.success` was never read; the flag-off branch (~723) does check it. J3 with a failing adapter: `workflow.completed success=False` and a workflow-level `execution.failed`, yet `orchestrator.query_completed outcome="success"`; J2: HTTP 200, `success: true`, empty answer.
