**Resolved (Sept 5, 2026):** ~~DEBT-003 — Checkpoint/resume not implemented~~. See `docs/architecture/decisions/ADR_KERNEL_03_CHECKPOINT_RESUME.md` for full detail. `WorkflowRuntime._save_checkpoint()` now writes a durable checkpoint (via the existing, previously-unused `EventStream.create_checkpoint()`) after every node boundary; `WorkflowRuntime.resume(definition, instance_id)` loads the latest one and continues, reusing already-COMPLETED nodes' cached results rather than re-running them. A node whose last known status was RUNNING at checkpoint time is reset to PENDING and re-executed from scratch, never assumed complete -- whether it actually finished before the crash is unknowable, and this project's Verification principle applies directly. A real bug was found and fixed by this work's own tests before commit: `_execute_from`'s existing "already executed, skip" short-circuit (added for diamond-shaped DAGs) does not distinguish "this traversal already visited this node" from "this node is already done" -- the two happen to be the same thing in every pre-resume caller, but not for a checkpoint-restored node, which is done without this traversal ever having reached it. Fixed with a per-traversal `visited` set. `ADR-KERNEL-01`'s own deferred I7 question ("revisit whether `WorkflowNode` needs `root_operation_id` once nodes are independently persisted") is answered: checkpointed node state is always nested inside one instance-keyed checkpoint, never independently addressable by node -- that decision stands, confirmed rather than revisited. Explicitly not attempted: the broader DEBT-015 architecture, automatic resume-on-startup discovery, restoring `execution_detail` on a resumed node's cached result, and side-effect idempotency (DEBT-015 sub-item 7, separately deferred). **Re-verified (Sept 16, 2026, Packet C governance/identity/provenance trace, findings register C-6):** independently re-traced this resolution's RUNNING→PENDING behavior against a different question -- not "does resume work" but "can persisted state become an authority substitute for a fresh governed decision" -- without reading this entry first (see this file's sync history for the honest process note on that). Confirms the resolution still holds exactly as described here four sessions later, and answers the authority-substitute question directly: no, for two structural reasons beyond what's recorded above -- `resume()`'s signature takes `instance_id`, not caller-supplied `node_states`, closing the obvious manufactured-state vector by construction; and every node that actually re-executes on resume re-enters the same governed `execute()` path as a fresh call, so resume never lets an already-performed action stand on a stale decision. Two bounded caveats added, not claimed as defects: (a) this guarantee assumes a trustworthy checkpoint store -- direct DB write access is a materially different threat model, not reachable through any traced runtime API; (b) `resume()`'s documented choice to start a fresh `ExecutionBudget` rather than restore one, combined with `DEBT-007`'s fail-open governance-layer budget check, means no mechanism imposes a cumulative ceiling across repeated resumes -- flagged as a cross-item interaction to be aware of at freeze, not a defect in either DEBT-003 or DEBT-007 individually. **Sharpened further (Sept 16, 2026, Packet D durability/retry/concurrency trace, findings register D-3):** this entry's own "explicitly not attempted: automatic resume-on-startup discovery" undersold how dormant the resume half of this mechanism currently is. A full production-code search (`interface/api.py`, `main.py`, `core/orchestrator.py`) found not merely no *automatic* discovery, but no caller of `resume()` at all -- no API route, no startup routine, no manual trigger of any kind. `resume()` also has no concurrency guard (no lock, no "already running" registry) against two concurrent calls on the same `instance_id`, which would be a genuine race if it could happen -- it currently cannot, since nothing calls it. Recorded as UNPROVEN rather than a live defect, consistent with this project's standing instruction not to escalate a dormant mechanism into a defect without evidence of exploitability. **Named revisit condition:** the day any caller of `resume()` is added -- a startup recovery scan or an API-triggered manual resume -- a concurrency guard on `instance_id` must be added in the same change, not after; until then, checkpoints are being written durably but the recovery half of "crash recovery" is unexercised outside tests. **Branch reconciliation (Sept 16, 2026, `audit/tracking-integration`):** C-6 and D-3 above were independently written on two separate local branches, each off a different point on `main`, each unaware of the other's addendum to this entry at the time it was written. Merged here without conflict of substance -- both describe the same resolved mechanism from different angles (authorization-boundary safety vs. reachability/concurrency) and agree with each other everywhere they overlap. This is the first instance of the cross-packet reconciliation Packet G's own stated job is to do at full scale; doing it once, early, at this small size confirmed the approach works before it's load-bearing for the whole freeze manifest.
**Resolved (Sept 7, 2026):** ~~CTX-DELETE-001 — `UnifiedMemory.delete()` returns `True` even when the authoritative L1 storage deletion fails~~.
